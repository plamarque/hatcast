# ADR-0010: V2 — Authentification via Google Cloud Identity Platform

- **Status:** Accepted
- **Context:** Le PRD exige **Google et email/mot de passe**, réinitialisation de mot de passe, sessions « se souvenir de moi », et une expérience proche de la **V1** (à l’époque **Firebase Authentication** côté produit legacy) sans réimplémenter côté HatCast le stockage des mots de passe, les flux forgot/reset, ni la politique de refresh multi-appareils. L’[ADR-0008](0008-v2-spa-auth-google-session.md) avait choisi **OIDC Google direct + session Spring + JDBC** et exclu Identity Platform pour le premier slice Google seul ; ce modèle **ne couvre pas** à faible coût opérationnel l’ensemble FR1–FR5 avec la même simplicité qu’un IdP managé.

- **Clarification — produit V2 (pas « Firebase » comme plateforme backend) :** La cible n’est **pas** de réutiliser **Firebase** (Firestore / Firebase Auth comme socle du runtime) comme en V1. Le service **souscrit et opéré** pour l’identité V2 est **Google Cloud Identity Platform** (console **GCP**). Certaines **bibliothèques** officielles pour parler à ce service portent encore le préfixe technique **`firebase`** dans le nom des paquets (ex. `com.google.firebase:firebase-admin`, package npm `firebase`) : cela reflète l’**API et les tokens** communs documentés par Google, **sans** faire de la V2 un projet « backend Firebase » au sens produit HatCast.

- **Decision:**
  1. **Fournisseur d’identité (V2):** Adopter **Google Cloud Identity Platform** comme service managé d’authentification (email/mot de passe, fournisseurs sociaux dont Google, reset par email, sessions multi-appareils — selon configuration du fournisseur).
  2. **Objectif produit:** Les utilisateurs peuvent se connecter avec **Google** et/ou **email + mot de passe** ; le produit peut s’appuyer sur le **linking de comptes** et les politiques du fournisseur pour rapprocher l’expérience **V1** (sans recoder les mécanismes sensibles en application).
  3. **Client (SPA):** Utiliser le **SDK client recommandé pour Identity Platform** (souvent le module **Authentication** du bundle documenté par Google ; les guides peuvent montrer des imports `firebase/auth` — **détail de packaging**, service = Identity Platform) configuré contre le **projet GCP** où Identity Platform est activé — pas de gestion applicative des secrets de mot de passe ni des emails de reset.
  4. **API (Spring):** Après connexion côté client, l’API valide les **ID tokens** émis pour le projet Identity Platform (issuer typique `https://securetoken.google.com/<projectId>`) via l’**Admin SDK** de vérification de tokens Google (**artefact Maven** `com.google.firebase:firebase-admin`, méthode `verifyIdToken`) ou mécanisme équivalent (JWKS + validation des claims). Les routes protégées exigent un principal dérivé de l’**identifiant utilisateur IdP** (`uid` / `sub` dans le token), pas un couple email/mot de passe traité par HatCast.
  5. **Référentiel métier:** **PostgreSQL** ([ADR-0009](0009-neon-postgres-environments.md)) reste la source de vérité pour **données métier** ; la table utilisateurs (ou équivalent) référence un **identifiant stable IdP** (souvent le `uid` Identity Platform) et synchronise email / nom affiché selon les besoins produit. HatCast ne stocke **pas** de hash de mot de passe pour l’auth Identity Platform.
  6. **Session navigateur ↔ API:** Choisir et documenter dans l’implémentation **une** des stratégies suivantes (ou hybride à court terme) : (a) **validation du Bearer ID token** (ou en-tête dédié) sur les requêtes API avec rotation gérée côté client ; (b) **échange ponctuel** ID token → **session serveur** (cookie HttpOnly) pour coller aux patterns CORS/CSRF existants. L’ADR n’impose pas l’une ou l’autre tant que les **menaces** (notamment **XSS** si tokens accessibles au JS) sont traitées dans la config sécurité et les revues.
  7. **Environnements:** **Projet GCP** (Identity Platform activé) **par environnement** (dev / staging / prod) avec clés Web, domaines autorisés et secrets distincts ; alignement avec **NFR-R1** (déploiements couplés SPA + API lors d’un changement de contrat d’auth).
  8. **Documentation et contrats:** Mettre à jour OpenAPI (`services/api/openapi/`), variables d’environnement et guides opérateurs (`docs/v2/`) pour refléter **Identity Platform** (clés Web, domaines autorisés, pas seulement OAuth Client « APIs & Services » isolé).
  9. **Supersedes:** Cette décision **remplace** l’orientation « pas d’Identity Platform pour la V2 » de l’[ADR-0008](0008-v2-spa-auth-google-session.md), désormais **Deprecated** (voir statut dans ce fichier-là).

- **Consequences:**
  - **Positive:** Moins de code et d’opérations sur mots de passe, reset, refresh ; parité fonctionnelle avec ce que la V1 offrait via **Firebase Auth** (sans réutiliser Firebase comme stack applicative HatCast) ; bénéfices GCP (facturation, support, options entreprise selon offre).
  - **Negative:** **Verrouillage fournisseur** sur la couche identité ; coût lié aux **MAU** / usage ; configuration à maintenir (domaines, clés, règles) par environnement ; le modèle **token** impose une discipline **XSS** et de validation serveur stricte.
  - **Migration:** Le code existant « GIS + `POST /v1/auth/google` + session JDBC » devient **legacy V2** jusqu’à bascule ; prévoir plan de migration des utilisateurs Postgres (ex. `google_sub` → **uid Identity Platform** / mapping) et mise à jour des user stories / epics en conséquence.

- **Alternatives considered:**
  - **Auth entièrement applicative (Spring + hash + reset + remember-me):** Rejetée comme stratégie par défaut — charge sécurité et conformité élevée pour un gain produit faible vs IdP managé.
  - **OIDC Google seul (ADR-0008 historique):** Insuffisant pour FR2–FR5 sans développements lourds côté HatCast.
  - **Autre IdP SaaS (Auth0, Cognito, etc.):** Non retenu dans cette ADR ; réévaluation possible si contraintes GCP / coût changent.
