## Analyse des preuves CI

- `.github/workflows/api-test.yml` exécute `./gradlew test` sur les changements API. Les trois classes `AdventMemberPostgresTest`, `AdventRankingPostgresTest` et `AdventResultPostgresTest` sont conditionnées à `ADVENT_TEST_POSTGRES_URL` ; ce workflow ne configure pas cette variable ni de service PostgreSQL. Leur exécution n'est donc pas démontrée par ce workflow. Chercher d'autres exécutions effectives et rapports avant de conclure qu'elles ne tournent jamais.
- `.github/workflows/apps-web.yml` lance le build ; les workflows examinés ne lancent pas `npm test -w @hatcast/web` / `ng test`. Les nombreux tests Angular, notamment d'identité et de réconciliation, ne constituent donc pas une protection CI démontrée ici.
- `.github/workflows/e2e-smoke.yml` lance `npm run test:e2e` et la configuration Playwright inclut `advent-answer` et `advent-member`. Les fichiers examinés interceptent `/v1/**` avec `route.fulfill` : ils testent l'interface avec API simulée, même si le workflow démarre un serveur. Ce n'est pas une preuve navigateur → API membre → base.
- Les déclencheurs CI sont filtrés par chemins ; vérifier les statuts réellement requis et les résultats sur le SHA candidat, y compris lorsque seuls des scripts ou configurations connexes changent. Zéro test sélectionné n'est pas une preuve de couverture.
- La sélection et l'exécution des tests d'isolation visuelle, motion et service worker nécessitent vérification séparée ; ne pas présumer leur inclusion dans `test:e2e`.

## Priorités proposées

1. **Rendre les preuves fiables** : faire exécuter en CI les tests Angular pertinents et les tests PostgreSQL sur base jetable locale ; contrôler les nombres réellement exécutés, skips et rapports ; conserver les tests API et Playwright existants. Rechercher d'abord d'éventuels jobs existants ailleurs.
2. **Ajouter un petit socle intégré** : données fictives isolées, vraie API membre et base, heure serveur maîtrisée sans commande accessible en production. Scénarios : fermeture et retour multi-appareils/multi-comptes ; réponse → minuit → révélation → autre appareil ; saut de jours et non-joueur ; confirmation incertaine/concurrente. Vérifier également le parcours d'entrée automatique depuis le shell, pas seulement `/avent` directement.
3. **Compléter les tests API ciblés** selon l'inventaire réel : frontières exactes, confidentialité des payloads, acquittement et pertes réseau, concurrence et privilèges. Ne pas compter des tests du seul parcours opérateur comme preuve du parcours ordinaire.
4. **Recette de livraison** : exécuter les suites sur la révision candidate, inspecter rapports et skips, vérifier catalogue et portraits dans l'environnement cible, réaliser une recette mobile/PWA et accessibilité ciblée, et investiguer BUG-062. Vérifier séparément la révision effectivement déployée.

## Décision

**Décision de livraison non évaluée** : il manque les résultats d'exécution sur un candidat identifié, l'état de la CI réelle, la preuve de bout en bout multi-appareils et la vérification de l'environnement et du contenu. La cartographie indique des risques et une stratégie, pas une certification de livraison ni la preuve d'un défaut fonctionnel.
