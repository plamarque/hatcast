## Boundary: three dates that must remain distinct

1. **Technical production availability:** June release/operations history and GR publications precede actual broad use. These establish a technical launch period, not an empirical opening boundary. The exact first launch date is unnecessary here and is not asserted. GR includes June 14 `v2.3.0` and June 19 `v2.4.0`; neither proves adoption. Exclude June–August construction releases from the empirical denominator for this retrospective.
2. **V1 cutover enabled in production configuration:** `bb07b52104067e4955ef16751a0f595018abd779`, July 12, sets `VITE_V2_CUTOVER_ANNOUNCEMENT_ENABLED=true` and destination `https://hatcast.app` in `.github/workflows/deploy-production.yml` (B02). Its same-tree `src/services/v2CutoverAnnouncement.js` interprets exactly `true` as enabled; `src/App.vue` displays a blocking “this version is no longer available” message, links to V2 and suppresses the normal app when enabled (B03/B04, App lines 7–49, 278 and 677–679). This is stronger evidence of an intended migration entry point than a mere banner draft. It remains repository configuration/code: this run did not establish the exact V1 deployment time, which clients loaded it, cache/update propagation, or subsequent use.
3. **Effective use:** Patrice's statement supplied for this research is that most users arrived in September and the exact opening date is unknown. Treat this as owner testimony with month precision, not a measured adoption series. Independent repository corroboration: B01/BUG-019 and B01/LIMIT-009 record organizer feedback dated September 16; BUG-020 records a September 16 scenario; BUG-021 records September 17 feedback. Their first committed registry record is `aaf7dbb4`, September 17, 11:00 +02:00. This is documented real-use feedback by mid-September, not evidence of the first user or that a majority had arrived by September 16. Feedback dates, registry commit dates, release publication and actual adoption are distinct.

**Recommended empirical design:** primary window September 1–October 23 inclusive, labelled “owner-informed September opening window”; sensitivity window October 1–23 inclusive, labelled “October established-use window.” September 1 is an analytical boundary, not a claimed opening day. Do not replace the primary window with June launch or July cutover merely because those dates are exact. The October subset reduces boundary ambiguity but has only four stable publications and can miss September migration/use defects; it does not prove all users had migrated. No percentages, active-user counts or usage weighting are supportable from these sources.

Seven stable publications are not seven independently comparable deployments. A case lacking incident records is “no incident found in these sources,” never “defect-free.”

## Interpretation safeguards for the later synthesis

- Pre-opening technical construction releases are contextual history, never additional empirical successes diluting post-opening failures.
- Release-time observations and later discoveries are separate columns. A later report associated with a running version is evidence of exposure, not introduction by that version.
- Product incidents, test-fixture defects, intermittent retries, staging served-identity incidents and post-deployment observability failures are different outcomes; none supplies a release-path category.
- Current issue blobs include later investigation and uncommitted material. The source import records HEAD, blob SHA256 and immutable historical versions so the synthesis can avoid hindsight leakage.
- Candidate chronology alone cannot supply complete CI run coverage, rejected-candidate counts, release lead time, user impact frequency or causal comparisons. Match with authorized run imports before calculating those measures.
