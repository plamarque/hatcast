# Ex ante release classification — frozen R1

Date: 2026-10-23. Unit: **complete delivered tag-to-tag release**, not the user-facing changelog item, semver, commit, story, or file count. Classification is a risk judgment, not a finding that a release succeeded or failed.

## Research rules

1. Never conclude from training data alone. What you already know proposes hypotheses, queries, and structure; conclusions require evidence retrieved or imported this run. A claim you cannot evidence is stated as an unverified belief or not at all.
2. The research firewall. Project context — briefs, PRDs, code, memory, persistent facts — shapes what to ask, never what is true. It is inadmissible as evidence: every claim in a research artifact traces to a digest or import file with a source. Here explicitly granted Git blobs/diffs are imported primary observations, not assumed project truth.

Evidence: [exante-sources.md](../imports/exante-sources.md), containing each interval's commit identities and complete changed-file inventory, full delivered source/test/configuration/script diffs, migration interval history, tag-specific test declarations and package scripts, and selected exact blobs. No current ISSUES contents, later commits, rollout memories, incident reports or proposal contents were consulted. Paths of changed documents appear only as inventory. Imported GitHub release notes were not needed for classification. Source review prioritizes production behavior and changed boundaries; inventory completeness does not mean exhaustive proof of every transitive dependency. No tests executed, no CI dispatched.

## Decision signal

**All seven actual release bundles classify Full under the stated conservative rule.** Confidence is high for six, medium for v2.6.0. This sample supplies no observed Fast release and no securely demonstrated Standard release. It supports retaining one complete path as the evidence-backed baseline for these bundles; it does **not** demonstrate that one path is optimal for every future maintenance correction. Separating units could plausibly make some corrections eligible for a lighter route, but this is counterfactual, not a historical count. Three operating paths are not justified by this sample. A second path would need a prospective trial and explicit boundaries, rather than relabeling bundled patch releases as Fast.

The weakest classification is v2.6.0: if a reviewer proves that multi-troupe privacy and shared-filter effects remain bounded and supplies the missing mapping, Standard becomes defensible. That sensitivity is explicit; the research does not force all three labels to occur.

## Migration status

For every predecessor/candidate interval, net `git diff --name-status` contains **no migration file added, deleted or modified**. An additional `git log --name-status predecessor..candidate -- services/api/src/main/resources/db/migration services/api/src/main/resources/db/migrations` also returns no migration changes. Thus none is classified Full because of a newly delivered SQL migration, and there is no observed add-then-delete migration in these inspected paths. This statement is path-scoped; it does not mean data behavior was unchanged: slot deletions, membership sync, session invalidation and recipient queries plainly change application behavior. Do not confuse absent schema migration with absence of data risk.

1. **Potential Fast: cancel-format dialog result repair inside v2.6.1.** The diff binds cancel to `undefined` and makes `EventInfosTab` validate structured results before PATCH. Evidence: the two exact UI paths and specs in the import. Existing event update API is retained. Callers to verify are dialog close/escape/backdrop and positive confirmation. 2. **Potential Fast, with parent-neighbor verification: stale unlock conflict UI inside v2.7.0.** [Commit 9e3e3ad](https://github.com/plamarque/hatcast/commit/9e3e3ad61b8040016a5cc87d8975be5f0e3cd433) modifies production `event-equipe-tab.ts` only, plus Équipe and parent event-detail tests (and documents excluded as evidence). No new server contract, auth policy, dependency, global PWA or external dispatch is introduced by this isolated code change. Review must still verify parent output wiring and existing API semantics; it is not counted as an actual Fast release.

Neither candidate proves that separate Fast and Standard administrative workflows repay their classification overhead. They demonstrate potentially isolatable work units, a different claim.

## Classification effort and uncertainty

No duration benchmark was performed; estimating minutes or savings would fabricate evidence. Ordinal effort from observed boundaries: v2.4.6 high (auth + UI + tooling), v2.5.0 high (audience/channel dispatch + fixtures/deploy), v2.6.0 high (privacy/aggregate compatibility + shared filters/tooling), v2.6.1 medium-high (one predicate across several neighbors + CORS), v2.6.2 high (delete/audit/notify/membership), v2.6.3 high (SDK + global PWA + build/promotion), v2.7.0 high (global recovery/cache + home/nav/analytics). A first pass can reject Fast once a disqualifying boundary appears; validating a lower route requires proving that no such boundary is hidden in the whole delivered unit. This asymmetry is visible in the inspected scope but is not a measured labor saving.

The seven-tag sample is provisional, consecutive only over the named window, and heavily bundled. It cannot establish a population distribution of maintenance risks, optimal path count, defect escape rate, CI time or failure correlation. Keep this R1 frozen before adding hindsight outcomes; compare outcomes later without rewriting the ex ante labels.

## Semantic and policy sensitivity note (same ex ante evidence)

The v2.6.0 read-only resolver is positive containment evidence: `resolveSeasonSlugReadOnly` resolves navigation without selecting/registering active troupe context, and its test asserts context and storage remain unchanged. Server `requireCanViewGlance` retains the existing active-membership check and applies it to every resolved troupe; the source does not show an intentional permission relaxation. Therefore Full here is a conservative **uncertainty escalation**, not proof of a global state mutation or an actual privacy defect. A policy accepting known read-only domain aggregation with these retained guards can reasonably label this release **Standard / medium**, producing one Standard and six Full bundles (and zero Fast); this supports investigating two paths but still provides no historical evidence for three. The cost of resolving this policy ambiguity is part of classification overhead. Shared file paths alone cannot settle it.

v2.6.3 likewise is not Full merely because PWA files changed. Many additions are analytics callbacks guarded against blocking existing actions. The semantic Full triggers are the actual PostHog dependency change, build-time release identity injection, and new dashboard provisioning/validation/promotion CI with external side effects, together with lifecycle observation spanning reloads. A policy that deems guarded instrumentation safe must still address those independent dependency/build/CI changes.

Cohort sensitivity: excluding the opening-transition v2.4.6 removes one high-confidence Full observation; it does not reveal an actual Fast bundle. Restricting further to v2.6.1–v2.7.0 leaves four high-confidence Full bundles. Exact opening/adoption dates are not inferred from Git.
