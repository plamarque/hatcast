---
topic: PostHog measurement of installed PWA adoption versus continued web usage
updated: 2026-10-17T15:27
---

- (direction by user) Measure how many HatCast users install the PWA versus continue to use it in a browser through PostHog.
- (capability) CAP-1: An identified HatCast user can contribute one session-level access-mode observation so operators can compare active PWA and web use.
- (capability) CAP-2: The product can record a confirmed native installation when the browser emits appinstalled, without treating this limited browser signal as universal installation proof.
- (capability) CAP-3: Operators can derive installed-PWA, web-only, and mixed-use populations over a selected period while excluding demo traffic.
- (constraint) Workflow analytics events must remain pseudonymous and bounded: no free text, third-party identifiers, email, name, browser fingerprint, raw user agent, or full URL in event properties.
- (constraint) The access mode must be detected from real browser state, including display-mode standalone and iOS navigator.standalone; stale local storage alone is insufficient.
- (constraint) PostHog remains disabled with no configured production key; instrumentation must remain no-op in local, CI, development, and staging unless explicitly configured.
- (constraint) Capture must use the centralized ProductAnalyticsService and keep person identification rules unchanged: internal UUID as distinct_id and existing M4 person-property exception is not extended.
- (decision) Use pwa_access_mode_observed with bounded access_mode standalone or web, deduplicated per identified person and browser session; use pwa_install_completed only for native appinstalled confirmation.
- (assumption) A user who has launched standalone at least once is counted as having used the installed application; a manual iOS add-to-home-screen cannot be counted at install time until it is launched.
- (question) What default reporting window should the PostHog recipe recommend: 30 days, 60 days, or another product cadence?
- (question) Should a person who used both standalone and web during the selected period be reported as a separate mixed-use segment or allocated to their most recent access mode?
- (note) Companion pwa-adoption-measurement.md carries the event catalog, bounded properties, browser-state rules, PostHog recipe, and verification contract.
- (event) Coherence validation passed: three capabilities have testable intent and success; constraints, non-goals, and concrete success signal are present; unresolved product choices are explicit open questions.
- (event) Preservation validation passed: user goal, installation-versus-use distinction, PostHog privacy constraints, platform limits, reporting segments, and authorization boundary for PostHog objects are represented; wrapper-only content dropped: BMAD workflow narration.
- (event) Spec finalized.
- (decision by user) Default PostHog dashboard reporting window is the most recent 30 days; users may change the dashboard date range without changing event collection.
- (event) Coherence validation passed after update: CAP-4 makes the graphical dashboard outcome testable; the 30-day default is constrained without limiting event collection.
- (event) Preservation validation passed after update: the user's 30-day dashboard request is represented in the kernel and measurement companion; existing privacy and authorization boundaries remain preserved.
- (direction by user) The dashboard is a PostHog-only artifact; HatCast must not implement a product-facing analytics dashboard.
- (capability by user) CAP-5: Product operators can inspect web-only users and compare their access mode by browser, browser version, operating system, operating-system version, and device type in PostHog.
- (constraint by user) Use PostHog's server-parsed event metadata for browser, browser version, OS, OS version, and device type; do not capture or retain raw user-agent strings or a device fingerprint in HatCast event properties.
- (decision by user) PostHog dashboard defaults to the last 30 days and includes adoption metrics plus compatibility breakdowns; identified web-only users are available through PostHog drill-down using existing authorized People identity properties, not new properties.
- (assumption by user) Version PWA means using HatCast as an installed standalone PWA rather than a browser tab; application build-version analysis is not included unless later requested.
- (event) Coherence validation passed after PostHog-only clarification: CAP-4 and CAP-5 are testable and dashboard scope no longer conflicts with HatCast UI non-goal.
- (event) Preservation validation passed after PostHog-only clarification: dashboard ownership, web-only user drill-down, compatibility metadata, and raw-user-agent prohibition are represented; wrapper-only content dropped: prior misstatement that implied a HatCast dashboard.
