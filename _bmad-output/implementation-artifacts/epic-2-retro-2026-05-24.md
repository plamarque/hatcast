## Challenges

### 1. Insufficient seed data → development in a vacuum

The seed did not provide realistic member data after Story 2.1. This forced the team to:
- Jump to Epic 3 stories to have something to show/test
- Add CSV import/export (Story 2.3) as a workaround to bootstrap data
- Build Story 2.3 without a fully stabilized user/member/participant distinction

**Root cause:** Seed was treated as an afterthought, not a prerequisite for demonstrable stories.

### 2. User / Member / Participant distinction not clear upfront

The boundary between `troupe_memberships` (Epic 2), season participants (`season_participants`), and event participants (`event_participants`) was not resolved before coding began. It was clarified incrementally — in Story 2.2 notes, then in Story 3.8 — too late for Epic 2 screens.

**Impact:** CSV contract revised twice in review; Story 2.3 AC6 realigned after two review cycles; admin screen semantics unclear (members tab vs participants label).

### 3. UX validated in parallel with implementation

UX-DR10 was approved while Stories 2.2 and 2.3 were already shipping their UI. This caused:
- Story 2.2 → dialog modal
- Story 2.3 → CSV grafted onto dialog
- Story 2.8 → full migration to route

Three layers on the same surface. The result feels patched — because it is.

### 4. Dense delivery pace → insufficient polish

All stories were implemented on the same day (2026-05-23). The cumulative effect:
- AC10 from Story 2.7 not implemented on `/compte` (preferred roles missing from account page)
- UI lacking polish and professional finish
- Story 2.6 had 7 review findings including non-trivial security issues

### 5. Multi-troupe UX not designed holistically

The multi-troupe switcher (Story 2.4) was built technically sound but without a deep UX reflection on the full user journey. The Admin Membres screen, the troupe context display, and the season navigation feel disconnected rather than part of a coherent flow.

---

## Key Insights

1. **Seed is a delivery prerequisite, not an afterthought.** No story should start without data that makes the scenario demonstrable from the first run.

2. **User / Member / Participant must be crystallized before the stories that manipulate them.** Ambiguity here cost time and produced patched code. This distinction should live in a shared doc (DOMAIN.md / SPEC.md) before sprint planning.

3. **UX must precede UI code.** A mid-sprint Correct Course is expensive. A validated spec upfront costs less.

---

## Strategic Decision

The multi-troupe user journey and the Troupes/Saisons screens need to be rethought before advancing to Epic 5. However, this refactoring is **scoped and timboxed** — not a full redesign — to keep the MVP goal (Epic 5/6: availabilities + weighted draw + full composition) in sight.

**Three surgical targets for the UX revision:**
1. Multi-troupe switcher + troupe home — just what creates onboarding confusion
2. Admin Membres screen — a UI polish pass (backend is sound)
3. Sign-in → troupe → season flow — coherence for a new user
